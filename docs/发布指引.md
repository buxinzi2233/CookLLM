# CookLLM 发布指引

本文档面向 CookLLM 的维护者，记录从「改代码」到「用户收到更新」的完整发版流程，以及踩过的坑。

## 零、docs/ 目录定位与纯文档更新规范

- `docs/` 目录仅用于存放项目文档、`README.md` 引用截图以及本发布指引，不参与 Tauri 应用源码编译与打包。
- **仅文档/截图变动时的提交规则**：如果某次改动**仅涉及 `docs/` 目录**（如更新截图、修改说明），只需要直接提交并推送到 GitHub `master` 分支：
  ```powershell
  git add docs/
  git commit -m "docs: 更新说明截图"
  git push origin master
  ```
- **重要准则**：仅 `docs/` 改动时，**严禁修改版本号**，**不需要重新编译**，**严禁打 `v*` Tag**（避免触发 GitHub Actions 的 Release workflow 生成多余安装包）。

## 一、版本号提升（推荐自动化）

### 推荐：使用发布自动化脚本

项目已提供发布自动化工具，一条命令自动同步 **6 处版本号**，并在 `CHANGELOG.md` 与 `README.md` 自动插入占位段落（同时自动按规范保留 README 最近 5 个版本）：

```powershell
# 提升小版本 (如 0.3.1 -> 0.3.2)
npm run release:bump -- patch

# 或提升次版本 / 主版本 / 指定具体版本
npm run release:bump -- minor
npm run release:bump -- major
npm run release:bump -- 0.4.0

# 可选：仅预览变更不写入
npm run release:bump -- patch --dry-run
```

### 备用：手工同步核对清单

若遇特殊情况需手动核对，6 处文件修改点如下：

| 文件 | 修改点 |
| --- | --- |
| `package.json` | `version` 字段 |
| `package-lock.json` | 顶层及 `packages[""]` 的 `version` 字段 |
| `src-tauri/tauri.conf.json` | `version` 字段（打包产物版本） |
| `src-tauri/Cargo.toml` | `[package] version` 字段 |
| `src-tauri/Cargo.lock` | `name = "cookllm"` 条目的 `version` |
| `src/data.ts` | `APP_VERSION` 常量 |

修改后可随时运行校验命令：

```powershell
npm run release:check
```

## 二、更新日志（必须，否则用户看不到更新说明）

**血泪教训（v0.1.4）**：`release.yml` 创建 Release 时没有携带 notes，导致用户从 v0.1.3 检测到 v0.1.4 后，应用内弹窗显示「本次更新未提供说明」。

发版时必须**两处同时更新**（运行 `npm run release:bump` 后会自动生成占位模版，需手动将 `- 待补充` 替换为真实说明）：

1. **更新根目录 `CHANGELOG.md`（必须）**：
   - 作为发布流程提取 Release Notes 的主要数据源。
   - 以 `## vX.Y.Z`（二级标题）开始写明本次改动，例如：

     ```markdown
     ## v0.3.2

     - 优化推理日志面板渲染性能
     - 修复深色模式下拉菜单边界反光
     ```

2. **同步更新根目录 `README.md` 的「✅ 更新日志」区块（必须）**：
   - 作为 GitHub 项目首页直观展示的最新动态。
   - 以 `### vX.Y.Z`（三级标题）开始写明本次改动，保持内容一致。
   - **注意**：`README.md` 的更新日志区块只保留最近的 **5 个版本**（`release:bump` 脚本已自动处理此截断逻辑；手动编辑时需注意删除第 6 个旧版本）。

3. `.github/workflows/release.yml` 会自动调用 `.github/scripts/get_release_notes.py --version X.Y.Z`：
   - 解析到对应段落 → 作为 GitHub Release notes 发布，应用内更新弹窗显示完整日志。

## 三、提交与发布（推荐自动化）

### 推荐：一键验证与安全发布

在确认版本号已提升、更新日志的「- 待补充」已替换为实际内容后，运行：

```powershell
npm run release -- --yes
```

该命令将全自动执行以下流程：
1. **严格校验**：校验 6 处版本号一致，且校验更新日志已填写完整（拦截未替换的「- 待补充」）；
2. **防重复发版**：检查本地 Tag 是否已存在；
3. **编译构建检查与本地安装包生成**：自动执行 `npm run build`、`cargo check` 以及 `npm run tauri build`，确保代码零报错并生成完整本地安装包产物（MSI & EXE）；
4. **安全暂存与提交**：仅精确暂存 6 处版本文件 + 2 处文档（绝不误提未暂存的临时/调试文件），创建 `release: vX.Y.Z` 提交；
5. **打 Tag 并推送**：打 `vX.Y.Z` Tag 并推送至 GitHub `master` 与 Tag，触发 GitHub Actions Release 打包流程。

### 备用：手工提交与打 Tag

若需手动执行发布：

```powershell
# 1. 验证编译与本地打包
npm run build
cargo check --manifest-path src-tauri/Cargo.toml
npm run tauri build

# 2. 提交改动
git add package.json package-lock.json src-tauri/tauri.conf.json src-tauri/Cargo.toml src-tauri/Cargo.lock src/data.ts CHANGELOG.md README.md
git commit -m "release: v0.3.2"

# 3. 打 Tag（必须带 v 前缀）
git tag v0.3.2

# 4. 推送 master 与 Tag
git push origin master
git push origin v0.3.2
```

推送 tag `v*` 会自动触发 GitHub Actions `Release` workflow，构建 Windows 安装包并创建 GitHub Release、上传 MSI/EXE 产物。

## 四、版本回滚 / 重新发布

- 如果发现发错了版本或构建失败：删除远端 tag 与 Release，修正后重新打 tag：

  ```powershell
  git tag -d v0.1.5
  git push origin :refs/tags/v0.1.5
  ```

  然后在 GitHub Releases 页面删除对应 Release，重新执行第三节流程。

- 注意：应用内「检查更新」读取的是 GitHub `releases/latest`，重新发布时确保新版本号高于已发布的最高版本。

## 五、构建产物与缓存清理

本地构建缓存占用空间排序（以本项目实测为准）：

| 路径 | 大小 | 说明 |
| --- | --- | --- |
| `src-tauri/target` | 约 15 GB | Rust 构建缓存，最大头，可整目录删除 |
| `dist` | 约 1 MB | 前端产物，可删除重新生成 |
| `.icons-build` | 约 4 MB | 图标构建缓存，可删除重新生成 |

清理前先关闭占用文件的进程（VS Code、rust-analyzer、cargo 相关进程），否则可能出现「访问被拒绝」。

```powershell
# 可选：备份后删除
Remove-Item -Recurse -Force src-tauri/target
```

删除后无需特殊处理，下次 `cargo build` / `npx tauri build` 会自动重建。

## 七、Linux 构建与发布补充

本节补充 Linux 工程准备；前述 Windows 安装包和自动应用更新描述继续用于 Windows。构建工作流就绪不代表云端已运行或已发布 Linux 版本。任何版本提升、提交、推送、Tag 和手动 Release workflow 执行，仍需维护者明确授权；普通本地打包与 Linux check 不发布版本。

### 1. 本地构建入口与兼容措施

- 在 Linux x86_64 仓库根目录执行 `npm run build:linux`，输出 deb / rpm / AppImage，目录为 `src-tauri/target/release/bundle/{deb,rpm,appimage}/`。Tauri 自动合并 `src-tauri/tauri.linux.conf.json`，基础 Windows 配置保持原样。
- `scripts/build-linux.mjs` 校验 Linux 平台，使用当前 Node 启动仓库本地 Tauri CLI，`shell: false`，透传 `--` 后参数与子进程退出码；不安装 CLI、不修改全局环境。
- 脚本仅在用户未设置时给子进程设置 `NO_STRIP=1`；Linux CI 显式设置该变量。原因是 CachyOS 上 linuxdeploy 内置 2024 旧 strip 对较新系统库 `.relr.dyn`（类型 `0x13`）报错。本应用 Cargo release 的 `strip=true` 保持原样，此措施不是关闭本应用优化。
- 本地 CachyOS x86_64 第四轮 `npm run build:linux -- --ci` 已成功，日志 `.tmp/linux-validation/final-upgrade/build.log`；主版本保持 `0.3.2`：`deb/CookLLM_0.3.2_amd64.deb`（2963190 字节）、`rpm/CookLLM-0.3.2-1.x86_64.rpm`（2964391 字节）、`appimage/CookLLM_0.3.2_amd64.AppImage`（113011192 字节），均位于上述 bundle 目录，完整摘要见 [累计验收记录](Linux验收记录.md)。本次只读日志与文档核对，不重跑构建/测试、未提交/推送/发布；开发机产物不构成最低 glibc 基线。Ubuntu 22.04 云端构建、Ubuntu 24.04 运行、Windows 回归和干净跨发行版安装仍需独立验收；旧 `/tmp` 构建日志仅作历史、不保证仍存在。
- 构建依赖和安装命令见 [README Linux 章节](../README.md#-linuxx86_64移植验证阶段)。锁文件当前使用 npmmirror 地址；本机 npm 12 已使用 `npm ci --registry=https://registry.npmmirror.com` 完成依赖准备。仅在需要安装依赖时执行，避免与其他构建进程并发安装；不修改全局 registry 或锁文件。

```bash
# Linux 定向门禁（后续主动验收时使用，本次仅文档同步）
cd /home/buxinzi/Projects/AI/LLM/CookLLM
# 依赖已有时不重复安装
```

### 2. 两类工作流及权限

| 工作流 | 触发与职责 | 权限 / 产物 |
| --- | --- | --- |
| `.github/workflows/linux-check.yml` | PR、分支 push 仅匹配源码、构建配置和相关脚本路径；也可手动验证。Ubuntu 22.04 / Node 22 / Rust stable，执行 `npm ci`、locked Rust check/test、两个 Linux Node 测试及三包构建。 | `contents: read`，上传 `linux-check-x86_64` artifact（14 天），不创建 Release。 |
| `.github/workflows/release.yml` build | 保留原 `v*` tag push / `workflow_dispatch` 发布触发；矩阵包含 Windows（原 Node 20 / `npx tauri build`）与 Ubuntu 22.04（Node 22 / `npm run build:linux -- --ci`）。 | 构建默认 `contents: read`，分别上传 `release-windows-x86_64`、`release-linux-x86_64`。 |
| 同一 workflow 的 publish | `needs: build` 等待两个平台成功，单一作业收集 MSI、EXE、deb、rpm、AppImage，检查格式齐全与资产名称冲突，生成 `SHA256SUMS` 后统一发布。 | 仅此作业 `contents: write`；没有第二个平台争抢创建 Release。 |

- Release workflow 使用固定 concurrency group 串行处理发布运行，构建矩阵仍并行。构建失败时 publish 不运行。
- 发布说明继续调用 `.github/scripts/get_release_notes.py --version "$VERSION"`，从仓库根目录读取 `CHANGELOG.md`（缺文件时使用 `README.md`）；保留现有提取失败后使用版本标题的回退。发版验收仍需确认 Release body 是真实完整日志，而非仅版本标题。
- Tag 触发使用 tag 版本；手动执行使用当前版本（选 tag 运行时使用所选 tag）。手动运行可创建缺失远端 tag，已有远端 tag 则复用；它仍是发布操作，不是验证按钮。发布目标为当前 workflow 的提交。
- `SHA256SUMS` 使用下载资产的原始文件名，可将所有安装包与摘要放在同一目录后执行 `sha256sum -c SHA256SUMS`。摘要用于完整性核对，不等于包签名；签名与发行信任策略另行确定。
